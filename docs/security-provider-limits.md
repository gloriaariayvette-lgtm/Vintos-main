# Provider-owned spend caps and usage alerts

Checked against public provider documentation on 22 October 2026. **Gloria sets these herself from a trusted device. No billing account was accessed or changed by this audit.** Dollar amounts, account tiers, current limits and notification recipients are unverified. This document grants no permission to buy credits, enable billing, raise a limit, change models or rotate keys.

These controls remain outside Aegis if it is compromised, provided Vintos has ordinary API keys rather than account/billing administrator access. Keep MFA, recovery codes and billing-admin sessions off Aegis and out of agent-accessible browsers. Use separate project/workspace keys for production and experiments. An account-level limit must cover all projects/keys; isolated per-key limits do not necessarily cap their combined spend.

## Choose amounts without authorizing new spending

For each provider, Gloria selects a monthly maximum she is willing to lose, `M`, and an experimental sub-budget within it. Use the provider dashboard's actual recent currency usage, not request count, to size `M`. Set alerts at 50%, 80% and 100% wherever supported, plus a low-balance alert. Route them to Gloria's independently controlled email/device, not only Aegis or its Slack bot. If the product lacks custom alert thresholds, record that gap and use an independent billing monitor or its native low-balance notification; do not invent a setting that is not present.

An API RPM/TPM rate limit bounds speed, not total dollars. A project “budget” can be only a notification. Prepayment without automatic refill reduces exposure but billing delay/concurrent jobs can overshoot. Confirm the dashboard's semantics before relying on any number as a hard stop. Never test a cap by deliberately consuming paid quota.

The host alarm counts requests to a provider, including status polls/errors that may cost nothing; billing pages measure currency/credits. Reconcile the two before diagnosing unauthorized charges. Direct realtime traffic after token minting is especially important: it can continue without further Aegis HTTP attempts.

## Acceptance record Gloria can keep

For each account, record provider, organization/project/workspace, selected `M`, cap type (enforced/alert/prepaid), overage/refill policy, alert thresholds/recipient, date checked and where to revoke credentials. Retain this record outside Aegis; include **no keys or payment details**. Confirm receipt of native administrative notices through ordinary use rather than deliberate spending. No such owner-account acceptance record was obtained in this audit.

If Aegis alarms disappear or usage suddenly rises, use these trusted provider pages first. A pause marker on Aegis is not evidence that a compromised host stopped spending.
